# Native Blog publishing

Prepared November 20, 2026. This replaces the unfinished Sanity Blog setup. The legacy Studio and its tests remain as inactive compatibility code; public Blog pages now read only `data/blog-published.json`. The eight Guides remain separate at `/insights`.

## Weekly use

The public `/blog` opens directly to the full latest edition, with its title, topic, publication date, reading time, section headings, lists and emphasis. No extra read-article step is required. Earlier editions appear below it, and each article retains its permanent `/blog/<slug>` URL for sharing. Both views use the same reader so published formatting stays consistent.

The reader presents each edition as a company post with its featured picture and photographer credit above the title, a compact publisher row, date and reading time, a comfortable single reading column, optional collapsible contents and a sharing footer. The complete article stays visible when contents are closed. No likes, views or comment counts are invented. Older text-only articles remain compatible; this image update does not rewrite the existing first article’s body.

1. Open `https://mycatalystinnovations.com/blog/editor` and enter the private editor password.
2. Paste Echo’s article and enter its title and topic. The URL is suggested from the title; the short summary can be entered or derived from the article’s opening.
3. Use **Featured picture** to choose a relevant image for a new article from the eight approved photographs. Keep its accurate default alternative text or write a truthful description of the picture. If none fits, ask Josh to review and add a suitable asset before publishing. Representative photos must not be described as Catalyst staff, clients, facilities or verified projects.
4. Select **Preview article**. Check the actual picture and credit above the title, then the entire text, sources, claims and formatting. Changing any field, picture or alternative text requires a new preview.
5. Select **Publish article** only after approving the actual content for public release. Publishing saves that exact version and starts the existing website deployment.
6. The **Article history** list shows each saved article, its dates, **Open to edit**, and its delivery status. **Saved · waiting to go live** means the latest version is stored but the public deployment has not caught up. **Live** means the exact saved version matches the public deployment, including the selected picture and alternative text. **Saved · live status unconfirmed** means the check could not be completed; it never guesses success. While a version is pending, this visible tab checks every 20 seconds. Deployment can take several minutes; do not publish the same article again. Use **View live article** and check the Blog listing before sharing its link.

Use blank lines for paragraphs, `##` for headings, `###` for subheadings, `-` for lists, `**bold**`, and `[source title](https://example.com)` for citations. HTML is displayed as text. Pasting rich text preserves its plain text; inspect the preview for formatting you want to add. Pictures come from the approved selector; file uploads, arbitrary image URLs and automatic image generation are not supported by this editor or publisher.

Select an existing article to revise it. Its URL and original publication date remain fixed. All publication dates use the New York calendar day. The regular editor keeps its eight-hour session. Josh has separately authorized Echo’s Friday articles without per-article approval; the dedicated, restricted browser publisher and its one-time private activation are described in [Echo’s weekly publishing handoff](echo-weekly-publisher.md). It uses neither the editor’s session nor a general account grant. Actual scheduled cloud-session reuse remains unverified until observed.

History shows the latest saved version of each article, rather than every Git revision. Previous versions remain in GitHub history. **Reload articles** refreshes the list; unsaved text stays in the form, and another preview is required. Automatic status checks preserve the open text, preview and edit revision. If another person saves a change, the editor asks you to reload rather than silently advancing that revision.

Opening an article restores its saved picture and alternative text along with its text. Existing text-only articles can remain text-only when revised. Once a picture is assigned, keep or replace it; a request from an older open editor that omits that picture is rejected rather than silently removing it. An image-only change is a real new version: it must be previewed, and an earlier save request cannot be reused to conceal the change. The separate Echo publisher remains disabled until Josh completes its private activation and cloud-browser sign-in; the existing Friday task has not been changed by adding pictures.

### Image rollout order

Deploy the image-aware code, schema, immutable assets and missing-image guards **before** adding featured-image metadata to the live article catalog. Confirm that DigitalOcean is fully serving that code, then make any approved existing-article image assignment in a separate content commit. Older running code strips fields it does not recognize; adding image data first could lose the metadata or compare a reduced version incorrectly. Keep the existing article body unchanged during an image backfill, and verify its new exact version after deployment. This does not authorize a public test post or activate Echo’s still-disabled publisher.

Text that has not been published exists only in the open editor page. Keep the original draft in Echo or your document. Closing, reloading, signing out or navigating away discards unsaved text. If a session expires, sign in using the separate-tab link, then reload the article list in the original editor to retain the pasted text. If a save result is uncertain, use **Retry publish** without changing the text; the same operation is checked instead of creating a duplicate commit.

## Storage, deployment and access limits

Delivery checks use the no-store public `/api/blog/publication-status` endpoint. It contains only the slugs and SHA-256 fingerprints of the validated articles bundled into the active deployment. The authenticated catalog compares all saved fields, including body, publication identifier, selected image asset ID and alternative text, against those versions. Same-day text or image changes cannot be mistaken for the older live version. Status requests send no editor cookie or GitHub token to that public endpoint. Failed checks leave articles available for editing and show an unconfirmed status. The status endpoint is excluded from search indexing and the sitemap.

The image catalog in `lib/native-blog-content.ts` reuses the eight licensed studio photographs documented in `docs/studio-media-sources.md`. Byte-identical copies are stored at `/blog-images/<SHA-256-of-file-bytes>.webp`, and that full immutable identity is saved as `featuredImage.assetId`. Dimensions, source, credit, license and representative-use caption come from the reviewed catalog. Do not overwrite those hashed files. A later replacement needs a reviewed catalog entry and new hash; Echo cannot upload or write asset files. No new provider, spending or environment permission is added by the selector.

The actual selected image is used for the article’s individual social metadata and BlogPosting image. Main article imagery reserves its known dimensions and receives loading priority; archive/related thumbnails load lazily. Alternative text describes the picture rather than repeating a keyword list. The historical SEO planning score remains unchanged: this feature alone is not a new performance or field Core Web Vitals measurement.

DigitalOcean App Platform local files are ephemeral. Published articles therefore save through GitHub’s Contents API to the fixed `data/blog-published.json` path on `main`. The app’s existing deploy-on-push pipeline builds that catalog into the public website. There is no extra database or Sanity account. Git history preserves previous published versions.

**This repository is public.** Selecting Publish makes the article public in source immediately, even if deployment is delayed or fails. Draft text is never written to GitHub. Published history is not a place for confidential content, and removing a public article later does not erase its Git history.

The API checks an eight-hour signed, HttpOnly, Secure, SameSite=Strict session and the exact allowed Origin before writes. Preview fingerprints confirm the posted content matches the previewed version; they are not proof of Josh’s identity or a second-person approval system. Anyone holding the editor password has publishing access. Login attempts are bounded to five per forwarded IP and 30 total per 15 minutes **per app process**. Redeployment/scaling resets this in-memory limiter; the global limit can also temporarily block legitimate sign-in. Confirm the host’s forwarded-IP trust and existing edge protections before wider access. No new edge provider is configured here.

Publication uses the catalog’s Git blob SHA to reject conflicts. Retry identity is checked against the published document and the latest 100 commits affecting the catalog. Older unconfirmed retries fail visibly rather than inventing a successful save. The collection is bounded to 900,000 UTF-8 bytes; individual article bodies are bounded to 60,000 characters. At that point, plan a reviewed storage upgrade rather than silently dropping content.

Published articles are public/indexable; editor metadata and HTTP headers are noindex, and the editor is omitted from the sitemap. The public reader contains no publishing token and does not contact GitHub or Sanity to render articles.

References: [DigitalOcean storage guidance](https://docs.digitalocean.com/products/app-platform/how-to/store-data/), [GitHub Contents API](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents), [fine-grained token limitations](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#fine-grained-personal-access-tokens-limitations).
